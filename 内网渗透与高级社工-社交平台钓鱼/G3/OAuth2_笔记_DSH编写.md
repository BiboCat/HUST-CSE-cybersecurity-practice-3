# OAuth 2.0 笔记：从零到整条链

> 本文用一个比方贯穿始终：**干洗店小票**（授权码）、**代客泊车钥匙 / 大衣**（访问令牌）、
> **公章**（客户端密钥）、**收货地址**（回调地址）。四个零件吃透，整条链就通了。

---

## 0. 先记住一句话

> **OAuth 是一套约定：让 A 网站，在不拿到你密码的前提下，得到你存在 B 平台的、你亲自点过「同意」的那部分数据。**

它本质是**授权**（authorization），不是登录。所谓「用微信登录」是后来盖在上面的一层（OIDC），见第 9.2 节。

---

## 1. 分清三个角色（这一步最容易乱）

**「你」这个字在这套东西里指两个人，必须先钉死。**

| 角色  | 本文统一叫法       | 是谁                         | 手里有什么                           |
| --- | ------------ | -------------------------- | ------------------------------- |
| 用户  | **你（用户）**    | 有平台账号的人                    | 账号密码、要保护的数据                     |
| 应用  | **应用 / 小网站** | 想读你数据的第三方                  | 登记的 `client_id`、`client_secret` |
| 平台  | **平台**       | 存你数据的那个（微信 / Google / 社区…） | 账号体系、授权端点、数据 API                |

一句话分工：

- **应用**想要你的数据
- **平台**替你保管数据
- **你**决定给不给

> ⚠️ 最容易搞混的一点：
> **`redirect_uri`（收货地址）属于「应用」，不属于「你（用户）」。**
> 用户连它是多少都不需要知道，连碰都碰不到。

---

## 2. 它解决什么问题

传统笨办法：小网站弹一个表单「请输入你的平台账号密码」。

为什么不行：

- **你不放心**：密码能干的事远不止读头像——还能发消息、改密码、转账
- **它也不放心**：服务器一旦被拖库，你的密码就没了，责任全在它
- **平台更不放心**

所以立下第一条铁律：**密码绝不交给第三方。**

改为：平台发一张**权限受限、自动过期**的临时通行证。

---

## 3. 四个核心零件

### 3.1 `access_token`（访问令牌）= 临时通行证 / 大衣

- 平台发的，凭它去访问数据
- 只能读你授权过的那几样（由 `scope` 决定）
- 几小时后**自动作废**
- **不记名**：谁拿到谁就能用，平台不认人、只认票（不绑 IP、不绑客户端）
- 用法：`Authorization: Bearer <token>`

### 3.2 `code`（授权码）= 干洗店小票

- 干洗店给你的小纸片，凭它去取大衣
- **小票 ≠ 大衣**，它只是**提货凭据**
- 平台通过**浏览器地址栏**把它送来（所以它必须在马路上跑，见第 6 节）
- **一次性**（用过即废）、**几分钟就过期**
- **光有小票取不到货**，兑换时还得报一个暗号

### 3.3 `client_secret`（客户端密钥）= 公章

- 注册应用时平台发给你的，**只有「应用」和「平台」两家知道**
- 作用：兑换小票时**证明「我是这家店」**
- **从不进浏览器**，只在那条「服务器直连服务器」的路上出现
- 配套的 `client_id` 是**店名**，**公开**的，只用来标识「哪家店」

**必须分清这一对：**

|                 | 是什么    | 保密吗 | 在哪出现            |
| --------------- | ------ | --- | --------------- |
| `client_id`     | **店名** | 公开  | 写在跳转网址里，满大街都看得见 |
| `client_secret` | **公章** | 绝密  | 只在后台通道出示        |

> 店名谁都能喊，**章盖不出来**。

### 3.4 `redirect_uri`（回调地址 / 收货地址）= 应用自己家的门牌

- 注册时登记，此后**一字不差**地比对
- 小票**只往这个地址送**
- **门后面站着的是应用自己的服务器**，所以「送到这个地址」就等于「送到应用手里」
- 属于**应用**，与用户无关

---

## 4. 注册应用：一切的地基

表单通常三项：应用名、**回调地址**、用途说明。注册完，平台一次给你**三样**：

| 平台给的            | 是什么            | 保密吗             |
| --------------- | -------------- | --------------- |
| `client_id`     | 你的**店名**，一串字符  | **公开**          |
| `client_secret` | 你的**公章**，更长的串  | **绝密**（通常只显示一次） |
| ——              | 你填的收货地址，被平台记下来 | ——              |

### 平台会先验证「这扇门确实归你」

否则谁都能填别人的地址，小票就全成别人的了。常见三种做法：

| 方式        | 你要做的                           |
| --------- | ------------------------------ |
| 放文件       | 在域名下放一个平台指定的文件，平台去访问一下，能读到就算你的 |
| 加 DNS 记录  | 在域名的解析设置里加一条平台指定的记录（TXT 之类）    |
| 加 meta 标签 | 在网站首页 HTML 里塞一段平台给的字串          |

验证通过后，平台存下一条**配套记录**：

```
client_id a3f9c2  →  redirect_uri https://a.com/cb
```

> **注意它不是「这个地址合法」，而是「这家店的货只能送到这扇门」。**
> 以后每次办事，都要拿这一对去核对。

**为什么这一栏要求最严？** 因为它是小票唯一的落地关口（第 6 节）。规范的原话是：**逐字符精确比较**，不忽略大小写、不忽略结尾斜杠、不认通配符、不许「先规整一下再比」。

## 5. 完整流程：五棒交接

场景：你在「A 站」点「用平台账号登录」。

### 第①棒：浏览器 → 平台（应用发起的跳转）

- **谁 → 谁**：A 站让你的浏览器跳到平台
- **走哪条路**：**前台**（浏览器地址栏）
- **带了什么**：

```
GET https://platform.com/oauth/authorize
     ?response_type=code                  ← 我要一张小票
     &client_id=a3f9c2                    ← 我是哪家店
     &redirect_uri=https://a.com/cb       ← 货送到哪扇门
     &scope=profile                       ← 我要哪几样数据
     &state=x8f2k1                        ← 随机串：防伪造 + 调试标记
```

- **谁看得见**：所有人（就在地址栏里）

### 第②棒：你 → 平台（登录 + 同意）

- **谁 ↔ 谁**：你和平台，**跟 A 站完全无关**
- 这一步 A 站**完全看不到**你输的密码
- 平台画出那一屏：「A 站 想要获得你的 头像、昵称　[拒绝]　[同意]」
- **这一屏是平台画的，不是 A 站画的**（看地址栏：是 `platform.com`）
- **产出：同意。这是发令枪——没点同意，小票根本不会产生。**

### 第③棒：平台 → 浏览器 → A 站（投递小票）

```
HTTP/1.1 302
Location: https://a.com/cb?code=8f3k2&state=x8f2k1
```

- **走前台**（浏览器地址栏）
- 浏览器自动跳过去，**A 站服务器日志里就多了一行**：`GET /cb?code=8f3k2`
- **小票就是这么到手的**：不是平台「发给」了 A 站，而是**浏览器把小票带到了 A 站门口**
- `state` 被原样带回，A 站比对一下（防止别人伪造一次回调打进来）

### 第④棒：A 站服务器 → 平台（后台兑换）★关键的一棒

```
POST https://platform.com/oauth/token
     grant_type=authorization_code
     &code=8f3k2
     &redirect_uri=https://a.com/cb     ← 必须和①里一模一样
     &client_id=a3f9c2
     &client_secret=<公章>
```

- **走后台**：A 站服务器**直连**平台服务器，**浏览器全程不参与**
- 平台核对：小票有效吗？公章对吗？地址和登记的一致吗？
- 返回：

```json
{
  "access_token": "at_9f3k...",
  "token_type": "Bearer",
  "expires_in": 7200,
  "scope": "profile"
}
```

### 第⑤棒：A 站服务器 → 平台 API（取数据）

```
GET https://platform.com/api/me
Authorization: Bearer at_9f3k...  加一请求头即可使用
```

- 拿到你的头像、昵称（以及你同意过的其他数据）

### 一图看全

```
你 ──① 点「用平台登录」──> 浏览器 ──跳转──> 平台
                                              │
                      ② 登录 + 点同意（平台画的那一屏）
                                              │
浏览器 <──③ 302 到 redirect_uri?code=... ─────┘
   │                     ↑ 走大马路（前台）
   └──> A站服务器（日志里出现 code）
              │
              └──④ 服务器直连，带 code + 公章 ──> 平台
                        <── access_token ───────┘
              │
              └──⑤ Authorization: Bearer ──> 平台 API ──> 你的数据
```

## 6. 为什么非要两条通道（本笔记最有价值的一节）

| 第几棒 | 走哪条路           | 谁看得见              | 送什么                    |
| --- | -------------- | ----------------- | ---------------------- |
| ③   | 浏览器地址栏（**前台**） | 满大街：历史记录、插件、旁人、截图 | **小票 `code`**          |
| ④   | 服务器直连（**后台**）  | 只有这两家             | **通行证 `access_token`** |

推理链：

1. 通行证**不记名**，泄漏 = 账号被人拿走几小时 → **绝不能放在吵的地方**
2. 但前台又**必须**有人跑腿：整件事的起因就是「你在浏览器里点了同意」，平台手上没有别的渠道能联系到 A 站
3. 于是让**小票**去跑那条吵的路
4. 小票被人瞄到也没用，因为：**一次性 + 几分钟过期 + 兑换要公章，而公章从不走前台**

> **一句话：前台只送「提货单」，后台才交「货」。值钱的东西永远不走大马路。**

## 7. 一张表：什么变，什么不变

| 参数                    | 每次授权会变吗  | 谁决定的     | 作用         |
| --------------------- | -------- | -------- | ---------- |
| `client_id`（店名）       | **不变**   | 注册时定的    | 标识是哪家店     |
| `redirect_uri`（收货地址）  | **不变**   | 注册时登记，写死 | 货只能送到这扇门   |
| `scope`               | 通常不变     | 应用决定要什么  | 要哪几样数据     |
| `state`               | **每次都变** | 应用随机生成   | 防伪造 + 调试标记 |
| `code`（小票）            | **每次都变** | 平台现场发    | 一次性提货凭据    |
| `code_verifier`（PKCE） | **每次都变** | 应用随机生成   | 临时暗号       |

规律：

> **身份类的不变，凭证类的每次都变。**
> 不变的用来「认出彼此」，变的用来「防止被重放」。

### 关于收货地址的两个方向，别搞混

- **横着看**（不同应用之间）：10 个网站 → 10 个地址 → **各不相同**，因为每家在平台登记的都是**自己家的门牌**
- **竖着看**（同一个应用，授权一百次）：**永远都是那一个**，一个字都不变

> **正因为写死了不变，平台手里才有「标准答案」可以比对。**
> 如果同一个应用每次地址都变，平台就没有标准答案，只剩「随便送」这一条路了。

## 9. 几个必知的扩展

### 9.1 PKCE：藏不住公章的客户端怎么办

**手机 App 和纯前端网页天生藏不住 `client_secret`**——App 能被反编译，前端代码按 F12 就能读。往里面写 secret，等于**把公章刻在门口招牌上**。

规范承认了这件事，打两个补丁：

1. 这类客户端叫「**公开客户端**」，**干脆不发** `client_secret`

2. 改用**一次一换的暗号**（PKCE，读作「匹克西」）：
   
   1. 发起请求前，客户端**现场随机生成**一串 `code_verifier`，自己留着
   2. 把它**算成一个指纹** `code_challenge`，跟着第①棒一起发过去
   3. 第④棒兑换时，把**原来那串 verifier** 交回去
   4. 平台一算指纹对得上 → 确认是同一个客户端

**好处：小票就算在路上被偷，没 verifier 也换不出令牌。**

### 9.2 OIDC / `id_token`：从「授权」到「登录」

- OAuth 原本只解决「**能不能访问数据**」，**没规定「这个人是谁」**
- OIDC 在 OAuth 上加了一个 `id_token`（一个 JWT），里面写着「这个人是谁」
- 分工：
  - **`access_token` → 用来访问数据**
  - **`id_token` → 用来告诉应用「他是谁」**
- 所以「用微信登录」= OAuth（拿数据）+ OIDC（确认身份）

### 9.3 `refresh_token`：免得反复弹同意

- `access_token` 只有几小时
- `refresh_token` 有效期长，用来在**后台**换新的 `access_token`
- 只发给能安全保存它的客户端（有后端的）

### 9.4 `response_type` 的其他取值

| 取值              | 名字    | 特点                                                                                                 |
| --------------- | ----- | -------------------------------------------------------------------------------------------------- |
| `code`          | 授权码流程 | 本笔记讲的，**主流、最安全**                                                                                   |
| `token`         | 隐式流程  | 第③棒直接回 `#access_token=...`。token 在 `#` 之后（fragment），**浏览器不会把 fragment 发给服务器**，只能被那个页面的 JS 读到。已基本淘汰 |
| `code id_token` | 混合流程  | 两者都给，常见于 OIDC。**校验代码路径常和纯 `code` 不是同一段**                                                           |

## 10. 设计上公认的薄弱环节（原理层）

1. **前台通道天生不可信**：小票在 URL 里，会进历史记录、Referer、代理日志
2. **收货地址的比对一旦放宽就出问题**：前缀比对、后缀比对、允许任意子域、忽略参数、忽略 scheme、先「规整」再比……**每一个「贴心」的处理都是一道门缝**
3. **店名和地址必须配套核对**：只查地址不看店名（或反之），等于发万能钥匙
4. **公章藏不住**：手机 / 前端写死 secret → PKCE 是补丁
5. **令牌不记名**：谁拿到谁能用，不绑 IP、不绑客户端
6. **`scope` 的「说」和「做」可能不一致**：同意页显示的、实际签发的、接口真正校验的，三者未必对得上
7. **`state` 缺失**：不致命，但给了伪造回调的空间
8. **不同 `response_type` 走不同代码路径**：同一条校验规则，在别的流程里可能根本没被执行

> **核心结论：整套机制的全部信心，建立在「这家店 ↔ 这扇门」这条记录被严格核对之上。**

## 附：最省事的入门方法

随便找一个支持「第三方登录」的网站，点一下那个按钮，**只盯着地址栏看**：

1. 地址栏会「唰」地跳到**平台**的域名（对应第①棒）
2. 你登录、点同意（第②棒）
3. 地址栏又「唰」地跳回**那个网站**的域名，末尾多了一小段 `code=` 开头的东西（第③棒）

**亲眼看一遍，胜过读十篇文章。**
